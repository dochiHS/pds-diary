## ① 무엇으로 붙였나

**인증 서비스: Supabase Auth** (GoTrue **v2.197.0** — `/auth/v1/health`가 돌려준 버전), 이메일·비밀번호 방식.

- 비밀번호 보관: Supabase Auth가 **bcrypt**(비용 10)로 되돌릴 수 없게 바꿔 `auth.users.encrypted_password`에 보관. 이 앱의 코드·DB 표는 비밀번호를 받거나 저장하지 않습니다.
- 로그인 뒤 사람을 알아보는 값: **토큰** — 액세스 토큰(JWT, **ES256** 서명, 발급 뒤 **3600초** 만료) + 리프레시 토큰. 토큰 안의 `session_id`로 서버의 세션 행(`auth.sessions`)을 가리킵니다.
- 토큰 보관: 이 브라우저 탭의 `sessionStorage`에만 두고, 요청마다 `Authorization: Bearer` **헤더**로만 보냅니다. 주소창(URL)·주소 뒤 `#`·쿼리에는 싣지 않습니다(`app.js` 맨 위 주석·`saveSession()`).
- 토큰 서명 비밀키: Supabase 서버 안에만 있습니다. 브라우저 코드·배포 파일(`config.js`)·Git 기록에는 공개용 **Publishable key**(`sb_publishable_…`)와 프로젝트 주소만 있고, Secret key·service_role 키는 없습니다(`app.js`가 `sb_secret_`로 시작하는 키를 넣으면 경고하고 멈춤).
- 브라우저 쪽은 라이브러리 없이 Supabase Auth REST API(`/auth/v1/signup`, `/token`, `/logout`, `/user`)를 `fetch`로 부릅니다.
- 자료 접근은 T06처럼 DB 함수(RPC)로만 하고, 함수가 토큰의 사용자와 세션을 확인합니다.

## ② 왜 그걸 골랐나

- T06이 이미 Supabase(DB + Data API) 위에 있어서, 같은 프로젝트 안의 Supabase Auth를 쓰면 **DB 함수가 토큰을 바로 믿고 확인**할 수 있습니다(서버를 하나 더 두지 않음). 토큰 서명 비밀키도 Supabase 안에만 있고 저는 만질 일이 없습니다.
- 비밀번호 해시·소금값·토큰 서명·만료는 직접 만들면 실수하기 쉬운 부분이라, 널리 쓰이는 서비스에 맡겼습니다(카드 2 C107). 비밀번호를 직접 다루는 코드는 이 저장소에 한 줄도 없습니다.
- **bcrypt를 쓰게 된 이유**: 제가 해시 방식을 따로 고른 것이 아니라, Supabase Auth가 기본으로 쓰는 bcrypt를 그대로 받아들였습니다. bcrypt는 계정마다 다른 소금값을 붙이고 비용(2^10번 반복)만큼 일부러 느리게 계산해서, 저장값이 새어도 한꺼번에 대입해 보기 어렵게 만드는 오래 검증된 방법이라 바꿀 이유가 없었습니다(argon2가 더 새롭지만 Supabase Auth에서 바꿀 수 있는 설정이 아닙니다).

**함께 검토했지만 고르지 않은 방법**

| 방법 | 고르지 않은 이유 |
|---|---|
| 직접 구현 (DB 안에 pgcrypto bcrypt + 세션 표) | 비밀번호·세션 만료·폐기를 모두 내가 책임져야 하고, 한 군데만 틀려도 전부 뚫립니다. 설명할 거리는 많지만 위험이 더 큽니다. |
| supabase-js 라이브러리 | 토큰 저장·갱신을 대신 해 주지만, T06이 외부 스크립트 없이 CSP로 같은 출처 파일만 실행하게 해 둔 것을 깨야 합니다. 필요한 호출은 REST 5개뿐이라 직접 불렀습니다. |
| Google 로그인(OAuth) | 비밀번호를 다루지 않아도 되지만, 로그인 결과가 주소(URL)에 실려 돌아오는 흐름이 생기고, 심사·시험 계정을 만들기 어렵습니다. |

## ③ 어디를 어떻게 고쳤나

네 흐름이 소스의 어디를 지나는지입니다. (소스 commit: 제출 때 고정 주소로 적음)

| 흐름 | 화면 `app.js` | 서버 |
|---|---|---|
| **가입** | `renderAuth()`의 가입 폼 → `signUp()` → `POST /auth/v1/signup` → `saveSession()`(탭의 sessionStorage) → `enterApp()` | Supabase Auth가 bcrypt로 저장하고 세션·토큰 발급. 같은 이메일은 422 |
| **로그인** | 로그인 폼 → `signIn()` → `POST /auth/v1/token?grant_type=password` | 틀린 비밀번호·없는 계정 모두 400 `invalid_credentials` → 화면 문구도 하나("이메일 또는 비밀번호가 맞지 않습니다.") |
| **로그아웃** | `doLogout()` → `signOut()` → `POST /auth/v1/logout?scope=local`(모든 기기: `global`) → 탭 토큰 삭제 | Supabase Auth가 `auth.sessions` 행을 지움 → 그 토큰은 `require_user()`에서 401 |
| **자료 조회** | `rpc()` — `Authorization: Bearer <토큰>`, 만료 60초 전 `refreshSession()`, 401이면 `endSession()`으로 로그인 화면 | `supabase/schema.sql`의 모든 공개 함수 맨 앞 `pds_private.require_user()` → `where id = … and owner_id = <토큰 사용자>` → 없으면 `pds_private.not_found()` = **404** |

그 밖에 T06에서 바꾼 곳

- `supabase/schema.sql`
  - `pds_private.require_user()`: ① 토큰의 `role = authenticated`와 `sub`(사용자) ② `session_id`가 `auth.sessions`에 살아 있는지. 둘 중 하나라도 아니면 401(`PDS401`). 서명·만료(exp)는 그 전에 Data API가 확인합니다.
  - 모든 표에 `owner_id` + `auth.users` 참조, 부모·자식을 `(id, owner_id)` 짝으로 묶는 `*_same_owner_fk` — 함수에 실수가 있어도 "남의 계획에 내 할 일" 같은 행은 DB가 만들지 않습니다.
  - 권한: 모든 함수의 실행 권한을 걷고 로그인한 역할에만 다시 줌. 로그인 안 한 역할(anon)은 `ping()`만(나머지 401). 표 직접 접근은 T06처럼 없음.
  - 표 사이 연결을 `RESTRICT → CASCADE`(계정 삭제 때 한꺼번에 지우려고. 화면·API에는 계획을 지우는 기능이 없음).
  - `delete_my_account()`: 확인 문구 "계정 삭제"를 받아 내 자료와 `auth.users`의 계정을 지움.
  - `pds_private.claim_t06_rows()`: 주인이 비어 있던 T06 행을 가입한 내 계정으로 옮기고 주인 칸을 NOT NULL로 잠금(값은 그대로).
- `index.html`: 공개 안내 → "내 기록은 로그인한 뒤에만" 안내, 로그인 전에는 계획·내보내기·메뉴를 숨김.

**AI에게 맡긴 일**
Claude에게 인증을 붙이는 코드(`app.js`의 가입·로그인·로그아웃·토큰 갱신, `supabase/schema.sql`의 `require_user()`·`owner_id`·404 처리), 로컬 검사, 실제 서버 확인 페이지(`auth-evidence.html`), 이 설명서 ①~④의 초안을 맡겼습니다.

**내가 직접 판단한 일**
인증을 T06과 같은 Supabase 안의 Supabase Auth로 붙이고 같은 저장소에 이어 올리기로 정했습니다. Supabase 설정(Confirm email 끄기, SQL 실행)과 T06 자료를 내 계정으로 옮기는 일은 제가 직접 했습니다. 확인 페이지는 제가 실제 서버에서 돌려 16/16 결과를 봤습니다. 5일 관찰 지표(그날 끝낸 할 일 수)와 바꿀 계획 규칙(할 날·시간대 같이 정하기)도 T06 돌아보기에서 제가 골랐습니다.

**AI 제안을 따르지 않은 일**
AI는 확인이 끝난 시험 계정 A·B를 정리하자고 할 수 있었지만, 승인 전 채점에서 다시 확인할 수 있게 남겨 두기로 했습니다.
